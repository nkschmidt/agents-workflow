# generate-project — генерация конфигурации проекта

Единая точка входа для старта/обновления проектной конфигурации (`PROJECT.md`) на базе framework `agents-workflow`. Запускается CDO по явной команде пользователя «изучи кодовую базу» (и синонимам). Идемпотентен: можно прогонять повторно для пересборки `PROJECT.md` после изменения состава рабочих областей.

## Когда применять

- Пользователь подключил рабочие области (субмодули / клонировал репо) и просит «изучи кодовую базу», «сгенерируй PROJECT», «инициализируй проект».
- `PROJECT.md` отсутствует (свежий проект) или устарел (состав рабочих областей изменился).

## Процедура

### Шаг 1 — определить корень проекта

Найти корень: каталог с `CLAUDE.md` + `framework.manifest` (подъём вверх от cwd). Если их нет — это не проект на базе framework; сообщить пользователю.

### Шаг 2 — проверить инициализацию, при необходимости поднять каркас

Проверить наличие:
- `memory/MEMORY.md` и скелета зон (`memory/_shared/`, папки агентов),
- git-remote `framework` (`git remote get-url framework`).

Если чего-то нет → запустить `scripts/init-project.sh` (он идемпотентен: создаёт скелет `memory/`, добавляет remote `framework` при наличии URL, выполняет первый vendor framework-файлов). Если `init-project.sh` не может определить URL framework — спросить пользователя.

### Шаг 3 — инспекция кодовой базы

Собрать факты для `PROJECT.md`:

1. **Топология:**
   - есть `.gitmodules` и каталог `submodules/` с выгруженными репо → `submodules`;
   - один репозиторий, рабочий код в корне → `single-repo`;
   - один репозиторий с несколькими рабочими зонами (workspaces/пакеты) → `monorepo`.
2. **Рабочие области:**
   - для `submodules` — распарсить `.gitmodules` (`path`, `url`); основную ветку каждого определить через `git -C <path> symbolic-ref --short refs/remotes/origin/HEAD` (фоллбэк: текущая ветка `git -C <path> rev-parse --abbrev-ref HEAD`);
   - для `single-repo`/`monorepo` — сам репозиторий (его `origin`-url и основная ветка); для `monorepo` дополнительно перечислить рабочие зоны.
3. **Назначение каждой области** — изучить её `README`, манифесты (`go.mod`, `package.json`, `Chart.yaml`, `*.tf`, плейбуки Ansible и т.п.), структуру каталогов; в одну строку сформулировать, что это и на чём.
4. **Описание проекта** — на основе инспекции всех областей: что за продукт/система в целом.

**Только чтение.** Рабочие области не модифицировать. Использовать `git -C <path> ...`, не `cd`.

### Шаг 4 — сгенерировать PROJECT.md

Записать `PROJECT.md` в корень проекта строго по шаблону ниже, заполнив реальными данными. Поле **Топология** — одно значение из `submodules | single-repo | monorepo`.

````markdown
# Project Config

> Проектная конфигурация для универсального регламента в `CLAUDE.md` (framework `agents-workflow`).
> Сгенерирован скиллом `generate-project` из кодовой базы. Поддерживать в актуальном состоянии при изменении состава рабочих областей.

## Описание проекта

<1–3 предложения: что за продукт/система, ключевой стек.>

## Топология

`<submodules | single-repo | monorepo>`

| Значение | Что означает |
|---|---|
| `submodules` | Мета-репо подключает рабочие репозитории через git-субмодули. Код правится внутри субмодулей. В мета-репо коммитятся указатели на коммиты субмодулей + общие инструкции/память. |
| `single-repo` | Один рабочий репозиторий. «Задействованные рабочие области» в §11 = сам репозиторий. Шага sync указателей (§11.7 п.2) нет. |
| `monorepo` | Один репозиторий с несколькими рабочими зонами. Ветки/PR — на уровне всего репо. |

## Рабочие области

| Путь | Назначение | Репозиторий | Основная ветка |
|---|---|---|---|
| `<путь/>` | <что это, на чём> | `<git-url>` | `<branch>` |
````

### Шаг 5 — отчёт пользователю

Показать сгенерированный `PROJECT.md` и кратко: какая топология определена, сколько рабочих областей, что попало в описание. Попросить пользователя подтвердить/скорректировать. `PROJECT.md` — проектный файл; апдейт framework его не трогает.

### Шаг 6 — предложить изучение архитектуры

После подтверждения `PROJECT.md` **предложить** пользователю запустить скилл `study-architecture` — глубокое изучение архитектуры по областям профильными агентами с записью в их память (чтобы доработки шли согласно существующим паттернам). **Не запускать автоматически** — операция дорогая и многоагентная, ждать явного апрува.

## Что НЕ делает этот скилл

- Не коммитит (коммит — по явной команде пользователя, §11.9 CLAUDE.md).
- Не модифицирует рабочие области и framework-owned файлы.
- Не заполняет память агентов проектным стеком — это отдельная задача (стек выявляется по ходу работы и сохраняется агентами в их память по §6/§7).
