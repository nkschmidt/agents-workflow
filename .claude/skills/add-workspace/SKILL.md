# add-workspace — подключение и онбординг новой рабочей области

Закрывает сценарий «проект уже инициализирован (`PROJECT.md` есть), пользователь хочет добавить ещё одну рабочую область». Один триггер вместо ручной цепочки `git submodule add` → `generate-project` → `study-architecture`. CDO-оркестратор; запускается **только по явной команде пользователя**.

Предусловие: проект инициализирован (`PROJECT.md` существует). Если нет — это старт проекта, а не добавление области → сначала `generate-project`.

## Когда применять

- Пользователь явно просит: «добавь сабмодуль `<url>`», «подключи новый репо», «я добавил область `<path>`, онбордь её», «add submodule / workspace».
- Топология проекта (из `PROJECT.md`):
  - `submodules` — основной кейс: подключается новый git-субмодуль.
  - `monorepo` — добавляется новая рабочая зона (пакет/каталог), уже существующая в репо.
  - `single-repo` — **неприменимо**: рабочая область одна (сам репозиторий). Сообщить пользователю.

## Процедура (оркестрация CDO)

### Шаг 0 — корень проекта, топология, предусловия

Найти корень по маркеру `framework.manifest` (подъём от cwd), как в `sync-submodules` (через `scripts/project-config.sh`: `find_meta_root`, `read_topology`, `parse_workspaces`). Проверить:

1. `PROJECT.md` существует. Если нет → проект не инициализирован, остановиться и предложить `generate-project`.
2. Топология ≠ `single-repo`. Если `single-repo` → сообщить, что добавлять нечего (область = сам репозиторий), остановиться.

Уточнить у пользователя недостающее: для `submodules` — `<url>` и `<path>` нового субмодуля; для `monorepo` — `<path>` новой зоны.

### Шаг 1 — подключить область (правка мета-репо)

**Топология `submodules`:**

- Если субмодуль ещё не подключён — выполнить подключение из корня мета-репо:
  ```bash
  git -C "$META_ROOT" submodule add <url> <path>
  git -C "$META_ROOT" submodule update --init --recursive -- <path>
  ```
- Если пользователь уже сделал `git submodule add` сам — пропустить, только убедиться, что область выгружена (`git -C "$META_ROOT/<path>" rev-parse HEAD`).

Это изменение мета-репо (`.gitmodules` + указатель). По §11.9 — **коммит только по явной команде пользователя**; в этом скилле не коммитим автоматически.

**Топология `monorepo`:** новая зона уже лежит в репо — git-действий на подключение нет, переходим к Шагу 2.

### Шаг 2 — обновить PROJECT.md

Пересобрать список рабочих областей в `PROJECT.md`, добавив новую. Делегируется логике скилла `generate-project` (он идемпотентен и инспектит код). Достаточно:

- инспектировать **новую** область (README, манифесты `go.mod`/`package.json`/`Chart.yaml`/`*.tf`/плейбуки, структуру) — в одну строку сформулировать назначение, репозиторий, основную ветку (по конвенциям Шага 3 `generate-project`);
- добавить строку в таблицу «Рабочие области» `PROJECT.md`, не затирая существующие строки и ручные правки пользователя;
- при необходимости освежить «Описание проекта», если новая область заметно меняет картину системы.

**Только чтение чужого кода**, через `git -C <path> ...`, без `cd`. `PROJECT.md` — проектный файл (апдейт framework его не трогает).

### Шаг 3 — изучить архитектуру новой области

Запустить `study-architecture` со **scope = только новая область** (скилл это поддерживает: «можно изучить только конкретную область — новый субмодуль»). Профильный агент (по стеку области: Go → `golang-expert-dev`, инфра → `devops-platform-engineer`, фронт → `frontend-expert-dev`) составляет architecture digest и пишет его в свою память; факты для других агентов — в `_shared/`. Это требует апрува как многоагентная операция — спросить пользователя перед запуском, если он не дал апрув заранее.

### Шаг 4 — отчёт пользователю

Списком: что подключено (path, url, short SHA для submodules), как изменился `PROJECT.md` (добавленная строка), какой агент изучил область и какие файлы памяти создал/обновил, что ушло в `_shared/`, найденные расхождения с документацией. Напомнить: коммит мета-репо (подключение субмодуля + указатель) и памяти — по отдельной явной команде (§11.9 / §6).

## Что НЕ делает этот скилл

- Не коммитит (ни мета-репо, ни память) — только по явной команде пользователя (§11.9 CLAUDE.md).
- Не модифицирует код рабочих областей (инспекция строго read-only).
- Не применяется к `single-repo`.
- Не запускает `study-architecture` без апрува (дорогая многоагентная операция).
