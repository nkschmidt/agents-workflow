# study-architecture — изучение архитектуры → память агентов

Онбординг агентов в кодовую базу: каждая рабочая область глубоко изучается профильным агентом, результат фиксируется в **памяти агента**, чтобы дальнейшие доработки шли согласно существующим слоям, паттернам и подходам.

Предусловие: `PROJECT.md` существует (если нет — сперва `generate-project`). Перезапускаемый: можно изучить только конкретную область (новый субмодуль, крупный рефакторинг).

## Когда применять

- Пользователь явно просит изучить архитектуру / онбординг агентов, либо подтвердил хэндофф из `generate-project`.
- **Только по явному апруву** — операция читает много кода и делегирует нескольким агентам.

## Принцип: код — первичный источник истины

**Кодовая база первична.** README, доки, комментарии, диаграммы — вторичны и **могут быть устаревшими**: использовать как подсказки и точки входа, но **проверять по фактическому коду**. Любое расхождение README/доки ↔ код фиксировать в digest отдельным пунктом «⚠️ расхождения с документацией».

## Процедура (оркестрация CDO)

### Шаг 1 — список областей и сопоставление с агентами

Прочитать `PROJECT.md` → рабочие области. Для каждой определить профильного агента по стеку/назначению:
- Go-бэкенд → `golang-expert-dev`
- инфраструктура (Ansible/k8s/CI) → `devops-platform-engineer`
- фронтенд → `frontend-expert-dev`

Неоднозначную область (несколько стеков / непонятно) — уточнить у пользователя. Если пользователь сузил scope до конкретных областей — взять только их.

### Шаг 2 — делегировать изучение (по study-brief)

Для каждой пары (область, агент) CDO запускает агента с brief'ом. **Передать агенту контекст** из его памяти (`memory/{agent}/`, `memory/_shared/`). Независимые области можно изучать параллельно.

Study-brief агенту:

> Изучи рабочую область `<path>` (**read-only**, код не модифицировать). Кодовая база — первичный источник истины; README/доки — вторичны, могут быть устаревшими, сверяй с кодом. Составь **architecture digest** по секциям:
> 1. **Слои и структура** — модули/пакеты, границы ответственности, зависимости между слоями.
> 2. **Поток данных / шина** — как данные ходят по системе; события, очереди, messaging, шина (если есть); синхронные/асинхронные пути.
> 3. **Паттерны и конвенции** — обработка ошибок, конфиг, DI/композиция, логирование/observability, валидация, подход к тестам.
> 4. **Точки входа и ключевые модули** — main/handlers/роуты/плейбуки; что читать первым при доработке.
> 5. **Команды** — build / run / test / lint (как они реально вызываются).
> 6. **Стек и версии** — языки, фреймворки, БД, брокеры, внешние сервисы, их версии.
> 7. **⚠️ Расхождения с документацией** — где README/доки врут или устарели относительно кода.
>
> Сохрани digest **в свою память** (это явное ТЗ): файл `memory/{твой-agent}/project_<area-slug>-architecture.md` с frontmatter (`name`, `description`, `type: project`) по правилам `memory/README.md`, и добавь строку-ссылку в `memory/{твой-agent}/MEMORY.md`. Факты, релевантные другим агентам (контракты между сервисами, общая шина, общая топология), вынеси в `memory/_shared/` с ссылкой. Ничего, кроме своей памяти, не создавай и не правь. Не коммить.

`<area-slug>` — короткое имя области (например `backend`, `infra`, `backoffice`).

### Шаг 3 — собрать и отчитаться

Собрать результаты агентов. Отчитаться пользователю: какие области изучены, какие файлы памяти созданы/обновлены, какие расхождения с документацией нашли, что ушло в `_shared/`. Предложить просмотреть digest-файлы.

## Запрещено

- Запуск без явного апрува пользователя.
- Модификация кода рабочих областей (изучение строго read-only).
- Запись агентом чего-либо помимо его памяти (`memory/{agent}/`) и оговорённого `_shared/`.
- Любые git-коммиты (коммит памяти — по §6/§11.9, отдельной командой пользователя).
