# Memory

Объединённая папка постоянной памяти проекта — для меня (CDO) и для агентов. Этот README — single source of truth по конвенции; CLAUDE.md только ссылается сюда.

## Layout

```
memory/
├── README.md                              ← этот файл (конвенция)
├── MEMORY.md                              ← мой (CDO) индекс
├── {type}_{topic}.md                      ← мои (CDO) записи (root level)
├── _shared/                               ← общая память агентов (читают ВСЕ агенты)
│   └── MEMORY.md
├── devops-platform-engineer/              ← память конкретного агента
│   └── MEMORY.md
└── golang-expert-dev/
    └── MEMORY.md
```

### Три зоны

- **Root level (`memory/*.md`)** — моя (CDO) память. Правила взаимодействия, регламент, общий обзор инфраструктуры без технических деталей.
- **`{agent-name}/`** — память конкретного агента. Технические детали по его зоне ответственности.
- **`_shared/`** — факты, нужные двум и более агентам сразу. CDO туда обычно не пишет.

Полное правило разделения зон — §7 CLAUDE.md.

## Что обязан читать каждый actor при старте сессии

| Кто | Что читает |
|---|---|
| CDO (я) | `memory/MEMORY.md` + все файлы, на которые он ссылается |
| Любой агент | `memory/_shared/MEMORY.md` + `memory/{agent-name}/MEMORY.md` + все ссылки оттуда |

## MEMORY.md (индекс)

В каждой зоне свой `MEMORY.md`. Общие правила:

- Всегда читается соответствующим actor'ом при старте.
- Лимит ~200 строк (после строки 200 контекст-менеджер Claude Code обрежет).
- Содержит **только ссылки** на отдельные файлы + одну строку-хук на каждую.
- Без frontmatter.
- Формат строки: `- [<title>](<file>.md) — <одна строка-хук>`.

## Отдельные файлы памяти

Один топик = один файл. Имя: `{type}_{topic}.md`, где `type` ∈ `user | feedback | project | reference`.

Примеры:
- `project_k8s_cluster.md`
- `project_backend_layout.md`
- `feedback_no_helm.md`
- `reference_grafana.md`
- `user_role.md`

### Frontmatter

```markdown
---
name: <kebab-case-slug, совпадает с именем файла без .md и без префикса типа>
description: <одна строка — используется, чтобы решить, релевантна ли запись запросу>
type: project | feedback | reference | user
---

<содержимое записи>
```

### Типы памяти

| Тип | Что хранит | Структура тела |
|---|---|---|
| `user` | Профиль пользователя: роль, цели, экспертиза, предпочтения | свободная |
| `feedback` | Правила «как работать» (что делать / не делать) | `<правило>` + `**Why:**` + `**How to apply:**` |
| `project` | Состояние проекта: инициативы, решения, сроки, инциденты | `<факт>` + `**Why:**` + `**How to apply:**` |
| `reference` | Указатели на внешние ресурсы (дашборды, тикеты, доки) | свободная |

### Связи между записями

Используй `[[<name>]]` для ссылок на другие записи (по полю `name:` во frontmatter). Если ссылаемой записи ещё нет — это нормально, это маркер «стоит написать».

## Что НЕ сохранять в память

- То, что выводимо из кода / git / `*.README` в репозитории.
- Эфемерное состояние текущей задачи (используй TaskCreate / план).
- Дубли уже сохранённого — особенно между зонами (root ↔ агент ↔ `_shared/`).
- Длинные логи, дампы вывода, временные снимки состояния.

## Жизненный цикл

- При обнаружении устаревшего факта — **обновляй или удаляй**, не дублируй.
- При первом упоминании факта, релевантного другому агенту — переноси в `_shared/`.
- Память версионируется git'ом. Изменения коммитятся вместе с задачей, которая их породила (§6 CLAUDE.md).
